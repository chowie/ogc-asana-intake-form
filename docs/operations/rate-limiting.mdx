Upstash Redis does two jobs:

1. **Accounts and sessions.** It holds users, invites, one-time links, and
   sessions. This is **required**. Without Redis, nobody can sign in. See
   [Authentication](/architecture/authentication#storage).
2. **Rate limiting.** Per-IP limits on the endpoints someone could abuse. This
   is best-effort and fails open.

## Limits

| Limiter id | Endpoint | Limit | Why |
|---|---|---|---|
| `login-request` | `login { email }` | 5 / 10 min | Stops email flooding through magic-link requests |
| `login-redeem` | `login { loginToken }` | 10 / min | Token guessing (on top of 256-bit tokens) |
| `login-google` | `login { googleCredential }` | 10 / min | Abuse of the Google token check |
| `register` | `register` | 10 / min | Invite-token guessing |
| `verify-email` | `verify-email { token }` | 10 / min | Token guessing |
| `resend-verify` | `verify-email { resend }` | 3 / 10 min | Email flooding |
| `create-invite` | `create-invite` | 20 / hour | Caps invite emails, even from an inviter's account |
| `chat` | `chat` | 20 / min | Anthropic spend |

`create-task` and `attach-task` aren't rate-limited. They already require a
live session, and Asana enforces its own limits. `session` and `logout` aren't
limited either.

## How it works

`netlify/functions/_shared/rate-limit.js` wraps `@upstash/ratelimit` with a
sliding window, using the shared client from `_shared/redis.js`. The client IP
comes from `x-nf-client-connection-ip`, then the first entry in
`x-forwarded-for`, then `'unknown'`.

Limiters are memoized per id, so a warm function instance doesn't rebuild them.
Redis keys are prefixed `rl:<id>`, for example `rl:chat` or
`rl:login-request`.

## Fail-open (limits) vs fail-closed (auth)

<Warning>
  When `UPSTASH_REDIS_REST_URL` or `UPSTASH_REDIS_REST_TOKEN` is unset, or the
  limiter call throws, `limit()` logs a warning and returns `null`, and **the
  request goes ahead**. Auth does the opposite: the same missing config means
  every session check fails, and nobody gets in.
</Warning>

Limits fail open because a brief Redis error during a limit check shouldn't
block a staff member who is already signed in. Auth fails closed because a
broken auth config shouldn't let strangers in. In practice, a missing Redis
config shows up right away as "nobody can sign in", not as quietly unlimited
traffic.

Look for these in the function logs:

```
[rate-limit] Upstash not configured — skipping limit for "chat"
[rate-limit] limiter error for "chat": <message> — allowing
[session] lookup failed: <message>
```

## Setup

<Steps>
  <Step title="Create a database">
    Free tier at [console.upstash.com](https://console.upstash.com). Any region
    works, but pick one near the Netlify function region. Use a **separate**
    database for local development, so test accounts stay out of production.
  </Step>
  <Step title="Copy the REST credentials">
    The database page shows `UPSTASH_REDIS_REST_URL` and
    `UPSTASH_REDIS_REST_TOKEN`. Use the REST pair, not the Redis protocol URL.
  </Step>
  <Step title="Set them in Netlify">
    **Site configuration → Environment variables.** Set both, then redeploy.
  </Step>
  <Step title="Verify">
    Sign in as an inviter. That proves auth storage works. Then request a magic
    link six times in a row for any email. The sixth request should return
    "Too many requests."
  </Step>
</Steps>

<Note>
  The free tier is far more than this app needs. Each authenticated request
  costs about two commands (`GETEX` on the session plus `GET` on the user),
  plus one limiter call where a limit applies.
</Note>

## Tuning

Limits are set as arguments where `limit()` is called, not in config:

```js
await limit(event, { id: 'login-request', max: 5, windowSec: 600 })
await limit(event, { id: 'chat', max: 20, windowSec: 60 })
```

Changing them means a code change and a deploy. Twenty chat calls a minute is
generous for one person (a full conversation is 4–5 calls) but caps runaway
spend from a single IP.

<Note>
  Limits are per IP, so a whole church office behind one NAT shares a bucket.
  The tightest limit is `login-request` at 5 per 10 minutes. If several people
  in the office request sign-in links at the same moment, they can hit it.
  Raise that limit if it becomes a problem; don't disable the limiter.
</Note>
