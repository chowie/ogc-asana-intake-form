Two endpoints are limited per IP:

| Endpoint | Limit | Why |
|---|---|---|
| `verify-passphrase` | 5 / minute | Passphrase brute force |
| `chat` | 20 / minute | Anthropic spend |

`create-task` and `attach-task` are not rate-limited — they already require a
valid signed token, and Asana enforces its own limits.

## How it works

`netlify/functions/_shared/rate-limit.js` wraps `@upstash/ratelimit` with a
sliding window. Client IP is read from `x-nf-client-connection-ip`, falling back
to the first entry in `x-forwarded-for`, then `'unknown'`.

Redis clients and limiters are memoized per key so a warm function instance
doesn't rebuild them.

## Fail-open

<Warning>
  When `UPSTASH_REDIS_REST_URL` or `UPSTASH_REDIS_REST_TOKEN` is unset, or the
  limiter call throws, `limit()` logs a warning and returns `null` — **the
  request proceeds**. Rate limiting is not enforced.
</Warning>

That's deliberate: a Redis outage shouldn't take the form down for six staff.
The tradeoff is that an unnoticed misconfiguration leaves production unlimited.

Check for it in the function logs:

```
[rate-limit] Upstash not configured — skipping limit for "chat"
[rate-limit] limiter error for "chat": <message> — allowing
```

The first in a production log means the env vars are missing. The second means
Upstash is reachable but erroring.

## Setup

<Steps>
  <Step title="Create a database">
    Free tier at [console.upstash.com](https://console.upstash.com). Any region;
    pick one near the Netlify function region.
  </Step>
  <Step title="Copy the REST credentials">
    The database page shows `UPSTASH_REDIS_REST_URL` and
    `UPSTASH_REDIS_REST_TOKEN` — the REST pair, not the Redis protocol URL.
  </Step>
  <Step title="Set them in Netlify">
    **Site configuration → Environment variables.** Both, or neither — one alone
    does nothing.
  </Step>
  <Step title="Verify">
    Enter a wrong passphrase six times quickly. The sixth should return
    "Too many requests."
  </Step>
</Steps>

Keys are prefixed `rl:verify-passphrase` and `rl:chat` in Redis.

## Tuning

Limits are arguments at the call site, not config:

```js
await limit(event, { id: 'verify-passphrase', max: 5, windowSec: 60 })
await limit(event, { id: 'chat', max: 20, windowSec: 60 })
```

Changing them means a code change and a deploy. Twenty chat calls a minute is
generous for a single user (a full conversation is 4–5 calls) but caps runaway
spend from one IP.

<Note>
  Limits are per IP, so an entire church office behind one NAT shares a bucket.
  If staff report spurious "Too many requests" during a busy week, raising the
  `chat` limit is the right fix — not disabling the limiter.
</Note>
