All secrets are server-side. None is bundled into client JS. The only `VITE_`
variable is `VITE_GOOGLE_CLIENT_ID`, and a client ID isn't a secret.

## Blast radius

| Secret | If leaked |
|---|---|
| `UPSTASH_*` | Read/write on accounts, sessions, and rate limits. An attacker could create an `active` user record and sign in as it, or disable or delete everyone. Only token **hashes** are stored, so existing links and sessions can't be stolen from it. **Treat this as the most sensitive credential** |
| `RESEND_API_KEY` | Send email as your verified domain (phishing that passes SPF/DKIM) |
| `ASANA_PAT` | Full access to the workspace as the token owner |
| `ANTHROPIC_API_KEY` | Anthropic charges for someone else's requests land on the church's account |
| `NOTION_TOKEN` | Read access to the roster database (names, emails, GIDs) |
| `GOOGLE_CLIENT_ID` | Nothing. It's public by design |

Scope `UPSTASH_*`, `RESEND_API_KEY`, and `INVITER_EMAILS` to the **Production**
deploy context (or point previews at a separate Upstash database). That way,
branch and preview builds never get production credentials. See
[Deployment](/operations/deployment#environment-variables).

`INVITER_EMAILS` isn't a secret, but it is a privilege list. Anyone who controls
an address on it can sign in and invite others.

## Rotating `UPSTASH_REDIS_REST_TOKEN`

In the Upstash console, **reset the REST token** on the database page. Update
the token in Netlify, then **redeploy**: functions only see new env values
after a deploy. Data is untouched, so sessions survive.

<Warning>
  Moving to a **new** Upstash database resets everything. All accounts,
  pending invites, and sessions are gone, and everyone is signed out. Inviters
  bootstrap again on their next sign-in, and everyone else needs a fresh
  invite. Avoid doing this on Sunday mornings and event weeks.
</Warning>

## Signing everyone out

There's no global secret to rotate anymore. To end every live session, delete
all `sess:*` keys in the Upstash **Data Browser** (or run `redis-cli --scan
--pattern 'sess:*'` and delete what it lists). Accounts are kept, and people
just sign in again. To remove a single person, see
[Inviting users](/operations/inviting-users#revoking-access).

## Rotating `RESEND_API_KEY`

Create a new key in Resend (sending access), update Netlify, redeploy, send a
test magic link, then delete the old key.

## Rotating `ASANA_PAT`

<Steps>
  <Step title="Create a new PAT">
    Asana → profile → **My Settings → Apps → Personal access tokens**.
  </Step>
  <Step title="Update Netlify">
    Set `ASANA_PAT` to the new value, then redeploy.
  </Step>
  <Step title="Test a submission end to end">
    Both `create-task` and `attach-task` use it, and `attach-task` also needs the
    preflight `GET` to succeed.
  </Step>
  <Step title="Revoke the old token">
    Only after the test passes.
  </Step>
</Steps>

<Note>
  A PAT belongs to a *person*, not the church. If that person leaves, task
  creation breaks. Consider whether it should be issued from an account the
  office controls.
</Note>

## Rotating `ANTHROPIC_API_KEY`

Create a new key in the Anthropic Console, update Netlify, redeploy, verify
Philip responds, then delete the old key.

## Rotating `NOTION_TOKEN`

Update it in Netlify, then **trigger a rebuild**. It is read at build time, so
it isn't used at all until a deploy runs. Watch
the build log for `[fetch-roster] Wrote N entries`.

## Hygiene

- `.env` is gitignored. Keep it that way.
- `.env.example` holds placeholders only — never paste a real value in.
- When someone leaves, set their `user:<email>` record's status to
  `"disabled"` and take them off `INVITER_EMAILS` if they're on it. Rotate `ASANA_PAT` if it was theirs.
- Netlify build logs are visible to anyone with site access; the functions log
  warnings but never log secret values.
